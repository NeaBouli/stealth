# TASK: OS-04 – Verified Boot, Attestation & System Integrity

## 1. Ziel des Tasks
Dieser Task implementiert die gesamte System-Integritätskette von GHOSTOS BlackRoot:

- **Verified Boot (AVB)** aktivieren und konfigurieren
- **Integrity Enforcement** für alle Systempartitionen
- **Hardware Attestation** (falls Gerät unterstützend)
- **Signaturbasierte Update-Kette** (OTA oder manuell)
- Schutz vor:
  - Manipulation des Bootloaders
  - Austausch des Kernels
  - Replacement-Angriffe auf System-Partitionen
  - Downgrade-Angriffe (Rollback Prevention)

Dies ist einer der sicherheitskritischsten Tasks des gesamten Projekts.

---

## 2. Anforderungen

### 2.1 Verified Boot aktivieren
Aktivieren von:

- Android Verified Boot (AVB)
- vbmeta Signaturen
- Rollback-Protektion
- Strict Partition Verification (Boot, System, Vendor, Product)

Konfigurationsdateien:

`rom_ghostos/boot/avb/avb_config.json`  
`rom_ghostos/boot/avb/avb_pubkey.pem`  
`rom_ghostos/boot/avb/avb_privkey.pem` (nicht im Repo, lokal gehalten)

### 2.2 Bootloader-Einstellungen
- Bootloader muss *locked* sein  
- OEM-Unlock deaktiviert  
- Verified Boot Mode = enforcing  
- Keine unsigned images flashbar  
- Kein Fastboot-OEM-unlock zulässig

### 2.3 Signatur der Systempartitionen
Folgende Partitionen müssen mit AVB signiert werden:

- boot  
- system  
- system_ext  
- product  
- vendor  
- odm (falls vorhanden)

Konfigurations-Skript:

`rom_ghostos/scripts/sign_partitions.sh`

### 2.4 Rollback-Prevention
- Versionszähler pro Partition
- Einstellungen in `avb_config.json`
- Schutz vor Downgrade-Angriffen (z. B. manipulierte ältere OS-Version)

### 2.5 Hardware Attestation (optional / empfohlen)
Nutzen der Hardware-Keys für:

- Verified Boot Status
- Boot-State (green/yellow/red)
- Nonce-based Attestation
- Proof-of-Integrity gegenüber Management-API (für Premium/OS)

Datei:

`rom_ghostos/ATTESTATION_NOTES.md`

## 5. Tests

### 5.1 Verified-Boot-Test
- Flashen eines unsignierten Images → **FEHLER (erwartet)**
- Flashen eines korrekt signierten Images → **BOOT OK**

### 5.2 Boot Status Check
- Bootloader zeigt "green" oder "locked" Status
- Kein Übergang in "orange"/"yellow" ohne Warnung

### 5.3 Attestation-Test (falls HW-Support)
- Generieren eines Attestation-Reports
- Prüfen von:
  - verified_boot_state
  - boot_state
  - os_version
  - os_patch_level

### 5.4 Downgrade-Test
- Versuch, ältere OS-Version zu flashen → **BLOCK**  
(rollback_index verhindert Downgrades)

## 6. Q&A (FAQ)

**F:** Müssen private Schlüssel im Git-Repo sein?  
**A:** Niemals. Private AVB-Schlüssel dürfen nur lokal und niemals im Repo existieren.

**F:** Können wir Verified Boot für Entwicklung abschalten?  
**A:** Ja, in Debug-Builds. Aber Produktions-Builds müssen strikt enforcing sein.

**F:** Was passiert, wenn Verified Boot fehlschlägt?  
**A:** Das Gerät startet nicht (brick protection). Dies ist gewünschtes Verhalten.

**F:** Funktioniert Attestation auf allen Geräten?  
**A:** Pixel-Geräte unterstützen es nativ. Andere Geräte können eingeschränkt sein.
