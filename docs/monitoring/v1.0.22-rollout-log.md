### 2026-04-17 03:41 EEST — Check #2 — YELLOW

**Railway Signaling (deploy: 763fb534, SUCCESS):**
- REGISTER success: 8 / reject: 0
- FCM persist: 3 / errors: 3
- 5xx/uncaught: 0

**Play Console:** (manual check required — noch kein Rollout gestartet)
**User-Reports:** 0 neue Issues
**Auffälligkeiten:**
- FCM persist EACCES auf `/app/data/fcm_tokens.json.tmp` — Volume gemountet (150MB, ID `143a832d`), aber Dockerfile `USER securecall` (uid 1001) hat keine Schreibrechte auf das von Railway als root erstellte Volume-Dir. In-Memory-FCM funktioniert, nur Persistenz über Restarts fehlt.
- Root Cause: `Dockerfile:21 USER securecall` + Railway Volume default-Permissions = uid-Mismatch
- Fix-Vorschlag: Dockerfile vor USER-Switch `RUN mkdir -p /app/data && chown securecall:securecall /app/data` hinzufügen, ODER Entrypoint-Wrapper der `chown` macht (braucht root-init). Alternativ: in server.js `writeJsonAtomic()` auf fehlende Schreibrechte reagieren und ggf. Fallback-Pfad `/tmp/securecall-data/` nutzen.
- Schweregrad: YELLOW (kein User-Impact da FCM in-memory OK, aber Daten gehen bei Redeploy verloren)
**Aktion:** Dockerfile-Fix als v1.0.23-Item einplanen (kein Hotfix nötig)
